# 业务模块组织方式

按业务职责选择结构，而不是按工程名称或某个旧模块套目录。首先判断模块是否维护自身业务数据、是否有对象生命周期、是否跨系统编排以及是否有多种实现。

## 1. 简单业务能力

适合通知记录、基础资料、简单规则维护。使用 `Facade → Domain Service → Entity/Mapper`；只有 HTTP 入口时可由 Controller 调用统一业务服务。一个 Service 可以同时读写，不必预先分出应用服务、读服务和写服务。

实体仅有少量行为并不要求状态机；基本字段记录也不必伪造复杂聚合。复杂度增长后再按实际职责拆分。

## 2. 有生命周期的业务能力

适合申请提交、审批、资源借用、任务执行。实体提供 `submit`、`approve`、`reject`、`complete` 等业务方法；写服务处理权限、幂等、加载和事务，Mapper 负责条件写入。

状态规则简单时放实体；状态与事件组合多时使用状态机。操作流水用于已有的幂等或审计需求；需要时与主记录同事务保存。查询复杂且独立变化时可增加 ReadService。

参考完整 [设备借用审批案例](complete-example.md)。

## 3. 跨业务流程编排

适合同时协调申请、预算、资源和通知的用例。使用 ApplicationService 调用本领域服务、其他业务公开契约和外部适配。它可以没有自身实体、Mapper 或数据库。

先写清步骤、不可逆副作用、失败与恢复策略，再选择同步调用、消息或其他机制。不要在多个领域的 Facade、Controller、Listener 中分别复制同一流程。

## 4. 多类型统一能力

不同资源类型有相同公开操作、不同内部规则时，使用统一 Facade 和策略接口，以工厂或注入的策略集合选择实现。相同执行骨架、少量步骤不同，可采用模板方法。

类型分支很少且稳定时，简单分支也可能更清晰；不为每个常量都引入工厂。策略接口的输入、输出使用内部业务语言，供应商专用对象留在适配层。

## 5. 缓存或原子资源操作

适合配额、计数、资源预占等需要原子执行的操作。领域服务可调用缓存客户端或原子脚本，把检查、更新和必要的操作记录放在同一原子范围内。

没有数据库就不生成 Mapper/DO。业务同时保留数据库和缓存时，分别定义权威数据、更新顺序、恢复来源、超卖/超额防护及缓存缺失行为，不称它们天然属于同一事务。

## 6. 外部服务与供应商接入

业务能力通过公开接口或内部能力接口表达，`infrastructure/channel/<供应商>` 处理协议、认证、签名、SDK、单位换算及错误转换。多个供应商共享稳定能力时再增加通用接口和工厂。

应用服务调用适配并取得结果。回调由接入端解析验证后调用业务入口，避免适配实现反向注入应用服务形成环。共享多个业务使用的技术能力，可放在独立公共模块；仅一个业务使用时留在该业务内部。

## 7. 查询实现与组合视图

数据库与搜索引擎有不同查询实现时，使用明确的查询能力接口或 ReadService 选择实现，写入仍有自己的权威路径。API 返回视图可以组合其他业务的公开查询结果，不暴露内部持久化对象。

说明分页、排序、搜索数据延迟和降级条件；“查询失败”和“结果为空”不能互相替代。数据库与搜索双写也不是仅加一个接口就能保证一致。

## 8. 启动、聚合与装配

仅负责组合依赖、启动服务和配置 Bean 的模块，不需要领域实体或 Mapper。判断一个模块是不是公开契约模块，应查看它是否包含业务实现和启动职责，不能仅凭 `api`、`interface`、`app` 等名称判断。

## 组合使用

一个业务模块可以同时属于多种方式，例如“有生命周期的申请域 + 外部审批供应商”。组合的是职责，不是把每种方式的全部目录叠加。实施前按 [功能实现步骤](adaptation-guide.md)列出需要的角色即可。
