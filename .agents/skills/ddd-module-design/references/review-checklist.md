# 实现验收清单

按目标需求选择适用项；不适用项无需增加实现。审查应指出具体职责和行为，不能只核对包名。

## 职责与依赖

- 是否先按业务规则和数据归属划分模块，公开能力与实现边界明确？
- 是否能指出入口、用例编排、实体行为、持久化和协议适配各在哪里？
- 是否遵循目标工程与用户已经选择的架构，而非强制重写？
- ApplicationService 是否有实际协调职责，而非仅多一层转发？
- 默认直接使用 Mapper 时，是否准确承认实体/服务的框架依赖？
- 新增 Repository、DO 或端口接口时，是否有明确隔离需求或既有约定？
- 跨业务是否通过公开契约，未直接访问对方的 Mapper？
- 是否区分 API Request/Response/VO、HTTP Param、领域内部输入与供应商 DTO？
- 没有数据库的能力、纯编排与启动模块，是否避免虚构实体和 Mapper？
- 类名、状态、字段和错误码是否来自目标业务，而非照搬案例？

## 业务行为

- 有生命周期的实体是否通过业务方法检查前置条件并一起修改字段？
- 非法操作抛错前是否避免留下部分内存变化？
- 状态与行为是否符合目标业务，而非复制其他领域的特殊规则？
- 简单业务是否避免不需要的状态机、读写分离、事件或工厂？
- 操作者是否来自可信边界，权限与租户/对象范围是否正确？
- 金额、数量、时效等约束是否按实际需求验证？
- DTO 转换、字段复制和 Mapper 是否保持各自职责，没有隐藏核心规则？

## 一致性与失败

- 幂等键、作用范围、唯一约束及相同键不同载荷的语义是否明确？
- 同请求重试与不同请求重复操作已完成对象是否分别处理？
- 重复成功是否说明返回原操作结果还是最新对象状态？
- 主记录、成功流水及其他必须一致的本地写入是否同事务提交？
- 异常是否越过事务边界或显式回滚；是否测试第一笔更新后第二笔写失败？
- 事务代理、自调用及异常捕获位置是否与设计一致？
- 版本条件、唯一冲突、条件更新或原子脚本失败是否被检查和处理？
- 并发重复请求可能先返回冲突时，是否有明确重试或回查策略？
- 外部成功、本地失败及超时是否有与需求相符的反查、重试或补偿？
- 是否避免把数据库事务描述为覆盖 HTTP、缓存、消息或新线程？
- 内存事件与虚拟线程的投递保证是否符合需求；可靠任务是否使用相应机制？
- Listener/Job 是否复用业务入口，避免多份互相冲突的规则？

## 验证与交付

- 是否仅引入目标需求需要的缓存、消息、锁、分片或分布式事务？
- 正常行为、权限、非法状态、幂等、并发与相关故障边界是否有适当验证？
- 事务集成测试是否通过真实代理和数据库读取验证，而不是只 Mock 写入？
- 测试是否验证可观察行为，而非只断言目录、名称或重复实现常量？
- 是否区分静态分析、已执行测试、模拟外部依赖和未验证范围？
- 适配案例时，是否已按目标工程替换依赖、业务规则和标识，并验证实际行为？
