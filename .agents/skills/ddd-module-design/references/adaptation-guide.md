# 功能实现步骤

## 输入与产出

输入是目标工程和具体业务需求。说明书提供职责划分，不替业务决定状态、权限、金额、期限或一致性要求。先从已有代码和需求中确认这些信息；不影响独立工作的缺失项可以明确假设，影响正确性的关键问题需向用户澄清。

产出是符合目标工程约定的实现，以及足以说明设计选择和验证范围的简短交付记录。复杂功能可以先记录结构和关键流程，简单改动无需生成大型架构文档。

## 第一步：确认业务边界

识别谁拥有数据和规则，谁提供公开能力，谁只是流程调用方。不要先按技术层生成全工程目录。核对根包、构建工具、语言版本、依赖、公开接口、异常与响应风格、事务方式和现有测试。

将需求中的名词直接用作候选业务概念，例如“借用申请”“审批人”“审批记录”；将动作作为候选用例，例如“提交”“批准”“驳回”。不要把说明书案例中的领域名和状态当成新业务要求。

## 第二步：选择必要角色

按 [业务模块组织方式](module-patterns.md)选择一种或几种模式。以下问题决定层次：

| 问题 | 选择依据 |
|---|---|
| 只有本地简单读写吗？ | 一个业务 Service 可足够，无需 ApplicationService |
| 对象有生命周期及自身规则吗？ | 增加实体业务方法，复杂状态再增加状态机 |
| 一个用例要组合多个业务或外部系统吗？ | 考虑 ApplicationService，明确失败恢复步骤 |
| 读写查询分别很复杂吗？ | 按需要拆 ReadService 与 ManageService |
| 多种类型共享能力且行为不同吗？ | 考虑策略/工厂/模板 |
| 是否只有 HTTP 调用？ | 可以使用 Controller 和业务服务，不要求额外制造 RPC Facade |
| 是否需要公开给其他业务调用？ | 定义稳定 API 契约，由 Facade 实现 |
| 是否接受实体与 ORM 框架耦合？ | 轻量方案直接 Entity + Mapper；纯领域要求下再增加 Repository/DO |

## 第三步：列出类的职责

对于每个需要的类，用一句话说明拥有的决定和依赖。使用目标工程的业务语言和既有命名。

| 角色 | 需要写清的决定 |
|---|---|
| API 请求/响应 | 调用者可提供什么，响应表达完成、受理还是重复结果 |
| Controller/Param | 允许提交的字段，操作者如何从可信会话获得 |
| Facade | 对外入口与异常转换，是否有简单编排 |
| ApplicationService | 跨边界的步骤顺序、外部调用与恢复路径 |
| Domain Service | 权限、幂等、加载、实体调用及本地事务边界 |
| Entity | 业务不变量、合法状态及一次操作会一起变化的字段 |
| Mapper | 查询范围、条件更新、版本、唯一键及影响行数语义 |
| Channel/Client | 协议输入输出、认证和错误映射 |
| Listener/Job | 触发条件、可重复执行的入口以及终止/重试条件 |

公开 Request/Response、Web Param、内部请求和供应商 DTO 由边界决定；不要求同一条数据经过没有隔离价值的四套对象转换。

## 第四步：描述一条正常路径和失败路径

先写下最重要的一条调用链，标明每次写入和外部副作用。完整本地写操作见 [设备借用审批案例](complete-example.md)。

```text
接入适配
  → 校验格式并获得可信身份
  → Facade / ApplicationService
  → Domain Service 加载与授权、检查幂等、调用实体
  → Mapper 按版本条件更新 + 保存操作结果
  → 提交本地事务
  → 转换对外响应
```

对本地写入，明确：对象不存在、无权限、非法状态、同键相同载荷、同键不同载荷、版本竞争、流水写失败。对跨系统用例，再明确：远程超时能否查询、远程成功本地失败、重试是否重复副作用，以及无法恢复时的可见状态。

不要在持有数据库事务时等待任意长的外部调用；也不要仅把外部调用移到事务外就声称一致性问题已解决。业务要求决定是否需要操作记录、中间状态、持久化任务、消息或补偿。

## 第五步：实现并验证业务边界

按目标工程已有测试与构建方式执行必要验证。优先证明行为：正常结果、权限、非法迁移、幂等语义、条件更新和事务回滚。新建一个与实现常量相同的断言不能证明状态设计正确。

涉及本地事务时，测试第一笔更新成功、第二笔写入失败后主记录是否恢复；涉及外部系统时，用适当的集成环境或明确替代依赖验证调用与恢复，不把 Mock 测试称为真实远程一致性验证。

## 第六步：交付

按 [验收清单](review-checklist.md)核对，说明新增位置、关键职责、采用的可选机制、运行的检查及未验证范围。明确目标工程约定覆盖了说明书哪些默认选择。

可使用以下请求启动一个功能：

```text
使用 $ddd-module-design，在目标工程实现【业务需求】。
先查看已有约定，再按说明书选择必要的分层和类。
说明关键职责、调用链和事务/幂等边界，随后完成实现与必要验证。
```

长期入口可选用 [AI 指令片段](../assets/AGENTS.fragment.md)。指令合并到目标工程时使用真实的目录和规则；整个技能文件夹可独立复制使用。
