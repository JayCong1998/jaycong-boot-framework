# 架构规范

## 1. 适用范围与默认选择

本说明书定义一套用于 Java/Spring 业务工程的轻量 DDD 分层：按业务能力组织代码，实体表达业务行为，领域服务协调本领域操作，Mapper 负责持久化。单体部署和多个独立服务都可以采用这些职责边界。

默认允许领域服务依赖 MyBatis/MyBatis-Plus Mapper，实体兼作数据库映射对象；不要求增加 Repository、独立 DO 或多套转换对象。这个选择适合重视交付效率、接受框架依赖的业务模块，不等于纯领域架构。用户明确选择其他依赖模型时，以该选择为准。

本文的“目标工程”是将要开发或修改的工程；“业务模块”是围绕一项业务能力组织的代码；“本领域”指该模块负责维护的业务规则和数据。相关名词见 [术语表](glossary.md)。示例业务名称、字段和状态仅用于说明角色。

## 2. 先分业务，再选择层次

先按业务规则和数据归属划分模块，例如采购、人员、设备、通知；然后在各模块内部选择必要的层次。一个业务能力可以只是包，也可以是 Maven/Gradle 子模块或独立服务，不能仅由目录名推断部署关系。

公开契约与实现分开：调用方依赖公开接口和数据契约，不直接访问另一个业务的 Mapper。独立 API 模块是契约发布方式之一；同一进程中也可以采用清晰的 `api/<业务>` 包。

只负责组合流程的模块可以没有实体和数据库；只负责缓存操作的模块可以没有 Mapper；启动装配模块只需要启动与配置代码。不为目录齐全制造没有职责的类。

## 3. 目录与职责

以下是可选目录的完整集合，不是每个模块必须生成的文件树：

```text
api/<业务>/
  <业务>FacadeService.java
  request/          # 公开操作请求
  response/         # 公开操作响应
  model/            # 对外查询视图
  constant/         # 需要公开的状态、类型或错误码

<业务>/
  controller/       # HTTP 适配
  param/            # HTTP 输入
  facade/           # 公开契约的实现
  application/      # 需要时增加的用例编排
  domain/
    entity/         # 业务实体及行为
      convertor/    # 对象转换
      statemachine/ # 需要时增加的状态迁移定义
    service/        # 领域操作及持久化协调
      impl/         # 需要服务接口与多实现时使用
    request/        # 领域内部操作输入
    response/       # 领域内部操作结果
    event/          # 需要时定义的业务事件
  infrastructure/
    mapper/         # 数据访问
    channel/        # 外部系统及供应商协议适配
    config/         # 技术配置与装配
  listener/         # 消息或事件入口
  job/              # 定时触发、重试和补偿
```

| 角色 | 应承担的工作 | 判断边界 |
|---|---|---|
| Controller | HTTP 参数、可信登录身份、调用入口、HTTP 响应 | 不直接写 SQL，不展开核心状态规则 |
| Param | 描述某个 HTTP 请求允许提交的字段及格式约束 | 不把权限身份字段交给任意客户端填写 |
| API Request/Response/VO | 跨调用边界传递操作和查询结果 | 不把数据库实体当作公共契约返回 |
| Facade | 实现公开接口，校验调用输入、选择能力、转换结果，组织简单流程 | 复杂协调下沉到应用服务；不替实体决定状态 |
| ApplicationService | 协调多个领域、外部系统或多步骤恢复 | 不复制各领域已经拥有的业务规则或数据访问 |
| Domain Service | 加载实体、业务权限与约束、幂等、调用实体、本地事务及持久化协调 | 可以直接用 Mapper；不必再套只转发的 Repository |
| Entity | 维护对象身份、有效状态与自身业务行为 | 不执行 HTTP、SQL、消息投递等外部副作用 |
| Convertor | Request/Entity/VO 等对象间的字段转换 | 不在映射表达式中执行核心业务流程 |
| Persistence Mapper | 数据查询、条件更新和插入 | 约束并发写入条件，不替服务决定业务流程 |
| Channel/Client | 外部协议、签名、SDK、供应商字段及错误映射 | 不反向注入应用服务形成循环依赖 |
| Listener/Job | 接收事件或定时触发，调用可复用业务入口 | 不复制一套与同步入口不同的状态规则 |

`facade/service`、`application/service` 或 `domain/listener` 可沿用目标工程已有组织。`convertor` 与 `converter` 的拼写选择保持目标工程内部一致。配置、异常和常量按使用范围归属，不要求全工程强制搬迁。

## 4. 调用关系与依赖选择

简单用例：

```text
Controller（可选） → Facade → Domain Service → Mapper
                                  ↓
                           Entity 的业务方法
```

复杂用例：

```text
Controller / Facade / Listener
               ↓
       ApplicationService
               ↓
 本领域服务 / 其他业务公开契约 / 外部协议适配
               ↓
        Entity + Mapper（本地操作）
```

这些是职责调用图。允许 `domain/service → infrastructure/mapper`，意味着没有要求所有编译依赖都指向 domain。需要纯领域时可改为领域端口加基础设施实现，但不能同时宣称实体依赖 ORM 又完全与持久化无关。

领域实体可以接收简单的公开请求或内部操作参数；若公开契约变化频繁，可在边界转换为内部输入。是否增加 Command/DTO 层由隔离需求决定。跨业务采用公开契约；技术依赖、部署边界和业务边界应分别说明。

## 5. 业务行为的放置规则

- 单个对象能独立决定的规则放实体方法，例如 `submit`、`approve`、`cancel`，方法先检查前置条件，再更新相关状态和字段。
- 需要加载数据、校验操作者、查询重复操作或协调多个对象的规则放领域服务。
- 需要多个业务系统协作或处理中间步骤失败的流程放应用服务。
- 请求格式放入口约束；权限和业务有效性不能只靠请求字段注解保证。
- 查询结果的展示字段在边界转换或查询服务组合，不让写入实体承担界面展示流程。

简单状态可直接在实体方法校验；状态、事件组合多且需要集中核对时增加状态机。没有复杂状态行为的数据记录，不必为了“充血”增加无意义方法。

## 6. 命名与服务拆分

`<业务>Service` 适合简单读写；`<业务>ManageService` 与 `<业务>ReadService` 适合读写复杂度值得分别维护时使用，不意味着必须采用 CQRS。只有确有多实现、替换或稳定调用契约时，才增加接口与 impl。

实体命名表达业务身份，方法命名表达业务动作；避免业务入口仅暴露通用 `updateStatus`。请求、响应、VO、Param 和内部参数各按所在边界命名。错误码表达调用方可处理的业务结果，不直接暴露供应商或数据库异常信息。

## 7. 写操作说明与执行规则

每个写用例明确以下内容：

1. 可信操作者、权限范围、输入及业务约束。
2. 幂等键代表哪次操作，其范围是否包含对象、事件和操作者；相同键不同载荷如何处理。
3. 合法前置状态及实体行为，区分重复同一请求与不同请求对已完成对象再次操作。
4. 必须同成同败的本地写入，例如主记录、操作流水和待投递任务。
5. 唯一约束、版本条件、条件 UPDATE 或原子脚本如何防并发；先查询再插入本身不构成并发保证。
6. 更新影响行数、唯一冲突和后续写失败怎样反馈与回滚。

有状态变更和成功操作流水时，通常在同一本地事务中写入。采用 Spring 声明式事务时，由独立 Bean 的公开方法承载边界；写入异常应越过事务代理后再被 Facade 转为失败响应，或采用明确的 rollback-only/事务模板方案。不能仅因方法有 `@Transactional` 就声称所有失败响应会回滚。

实体转换、映射和 DTO 复制不能取代业务校验。金额、数量、时效、状态和权限均基于目标业务定义，不因为案例存在就假定已经验证。

## 8. 外部调用、缓存和异步

应用服务通过业务接口发起外部操作，适配实现处理协议、签名、单位转换和外部错误，返回内部可理解的结果。回调入口先验证来源与载荷，再复用业务入口；适配实现不通过反向依赖应用服务来处理结果。

数据库本地事务不自动覆盖 HTTP、缓存、消息或新线程。外部成功但本地失败、请求超时、重复回调、消息重复均需按业务要求定义结果查询、幂等、重试或补偿。不得把方法名、注解或注释当作运行保证。

本地事件和虚拟线程适合能接受进程退出丢失的任务；需要可靠投递时可选持久化任务、事件记录或消息机制，并明确提交与发送边界。重试任务复用同一用例，不另写状态规则。查询失败不能默认等同操作失败。

## 9. 按需选择机制

| 需求 | 可选组织方式 | 使用条件 |
|---|---|---|
| 多状态互斥操作 | 实体行为 + 状态机 + 操作流水 | 有实际状态约束和追踪要求 |
| 多种资源类型 | 统一 Facade + 策略/工厂/模板 | 行为确有相同点与差异 |
| 缓存原子计数 | 领域服务 + 原子脚本 | 确有缓存一致性方案，不能虚构数据库实体 |
| 数据库/搜索查询切换 | 服务契约 + 查询实现 | 需要替换查询来源，写入职责仍明确 |
| 跨域多步骤用例 | ApplicationService | 需要协调多个业务或恢复失败步骤 |
| 分布式锁、MQ、分片、分布式事务 | 适合目标工程的技术实现 | 源于并发、吞吐或一致性需求，而非分层标签 |

使用 [组织方式](module-patterns.md)选择结构，按 [完整案例](complete-example.md)理解一次端到端写操作，再用 [验收清单](review-checklist.md)核对实现。
